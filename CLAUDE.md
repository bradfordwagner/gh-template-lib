# CLAUDE.md

## What this is

Reusable GitHub Actions workflows (`on: workflow_call`) that build multi-arch images from a consumer repo's
`config.yaml`. It replaces the Dagger module `bradfordwagner/dagger-container-builds` (last tag `0.4.1`) and keeps
its contract, so a template switches by replacing its jobs with one `uses:` line.

## Layout

- `.github/workflows/<flavor>.yml`: one reusable workflow per `flavor:` value (`mirror`, `custom`,
  `ansible_playbook`, `ansible_role`). Only `mirror` is implemented; the others are stubs that fail with a TODO.
- `.github/workflows/ci.yml`: this repo's own CI (yamllint, actionlint with shellcheck, tests). Not callable.
- `test/`: shell tests. `test/fixtures/<flavor>/` holds configs and expected outputs.
- `docs/migration.md`: the plan for moving each template off Dagger.

## Contract (must not drift)

The `product` output is the build matrix, and it must match what `dagger-container-builds@0.4.1` printed for
`product-json`, byte for byte, including Go's `json.Marshal` escaping of `&`, `<` and `>`:

- `builds × archs`, in config order, `index` counting from 0. Ordering is part of the contract.
- mirror entry fields, in order: `repo`, `tag`, `arch`, `runner`, `target_image`, `commands`, `index`, `display`.
- `target_image` = `<target_repo>:<version>-<repo_override or repo>_<tag>`, no arch suffix.
- `display` = `<index>:<repo>-<version>(<arch>)` (uses `repo`, not `repo_override`).
- `runner`: exactly `linux/arm64` maps to `ubuntu-24.04-arm`, anything else to `ubuntu-24.04`. The one intended
  difference from Dagger: with ARC on, arm64 entries get `arc_runner_label` instead.
- Scalars are taken as their YAML source text (`tag: 3.10` is `"3.10"`), as yaml.v2 did.
- Per-arch tags are `<target_image>-<os>_<arch>`; `manifest` combines them into `<target_image>`.
- ansible_playbook entry fields, in order: `arch`, `os`, `runner`, `target_image`, `upstream_image`, `index`,
  `display`. `target_image` = `<target_repo>:<version>-<os>`, `upstream_image` =
  `<upstream.repo>:<upstream.tag>-<os>`, `display` = `<index>:<os>-<version>(<arch>)`. Fixtures in
  `test/fixtures/ansible_playbook/` come from `builds/ansible` `ProductJson`, run the same way.

`test/mirror-product.sh` runs the product step straight out of the workflow file against the fixtures. The
`<name>@<version>.json` fixtures were generated by running the Dagger module's `builds/mirror` `ProductJson` Go
code unchanged, outside the engine; `+arc` variants swap the arm64 runner. Never hand-edit them to make a test
pass. Add a fixture for every behaviour you change.

## Conventions

- Logic lives inline in the workflow `run:` blocks, reading only `env:`. A reusable workflow cannot learn its
  own ref, so a composite action or script in this repo would have to be pinned separately and could drift from
  the workflow calling it. Inline keeps one tag = one behaviour, and the tests extract the step with `yq`.
- Never interpolate `${{ }}` into `run:`; pass values through `env:`.
- Actions are pinned by digest with the version in a comment; Renovate (`helpers:pinGitHubActionDigests`) bumps
  them. Tool versions sit under a `# renovate:` comment on the line above.
- Hosted runner names are pinned (`ubuntu-24.04`), never `-latest`.
- `buildx build` runs with `--provenance=false --sbom=false` so each per-arch tag is a single image manifest.
- The registry caches are optional and off by default; refer to them only by their `host.k3d.internal:500x`
  address.

## Releasing

Consumers pin a tag: `uses: bradfordwagner/gh-template-lib/.github/workflows/<flavor>.yml@<tag>`. Cut semver
tags from `main`; a breaking change to inputs or the product contract is a major bump. A change reaches a
template only after its pin is bumped (Renovate does this).

## Commands

```sh
./test/mirror-product.sh
```
